# Reference — what the converter does today

This page is the what: the settled current state of how DAX3 XML fields map
to the generated EasyEffects preset, the plugin chain, units, and what's
deliberately left out. [design-notes.md](design-notes.md) and
[docs/research/](research/) hold the why: the research log, superseded
hypotheses and what was attempted.
[cross-device-findings.md](cross-device-findings.md) holds the empirical picture
across ~2,800 DAX3 files, and [corpus.md](corpus.md) what that collection is
made of.

> **Core invariant:** every parameter emitted traces to a parsed DAX3 XML
> field. There are no per-device hand-tuned offsets. The XML→param mappings
> below are hypotheses about the schema. DAX captures are the only signal that
> can falsify them. The research log, [design-notes.md](design-notes.md) and
> [docs/research/](research/), holds the evidence behind each.

## Repository layout

The repo root is the command surface: only files a user types live there.

| Path | What it is |
|---|---|
| `dolby_to_easyeffects.py` | generator: DAX3 XML → EasyEffects preset |
| `ee_to_pipewire.py` | converter: EE preset → PipeWire `filter-chain` conf |
| `dolby_to_pipewire.py` | one-command wrapper around both |
| `lib/` | everything the three are built from |
| `tests/` · `tools/` · `docs/` | suite, maintenance and measurement tooling ([index](../tools/README.md)), these notes |

Those three paths are load-bearing well outside the code, so they stay put. The
README, the [issue template](../.github/ISSUE_TEMPLATE/device-report.yml), the
`register-python-argcomplete` line, and the emitted `_generator` and
`# Generated by` provenance stamps all name them. Any module that is *not* an
entry point belongs in `lib/`.
`tests/test_layout.py::test_root_holds_only_entry_points` enforces that.

`lib/` sits at the repo root rather than under `src/` because nothing here is
ever installed. The root is already on `sys.path` wherever it matters: a
script's own directory, `tests/conftest.py` and the `tools/measure_*` harnesses.
So `import lib.version` resolves at each of them with no path juggling.

What `lib/` contains grows with every extraction, so its contract is a rule
rather than an inventory: whatever `ee_to_pipewire.py` reaches at startup is
**stdlib-only**. The converter does no DSP and must not pay for numpy/scipy to
translate a preset. A shared module that needs the DSP stack therefore either
imports it inside the function that wants it, or lives somewhere the converter
never touches. `tests/test_layout.py::test_converter_startup_pulls_in_no_dsp`
enforces exactly that, from the converter's end. It imports `ee_to_pipewire.py`
in a subprocess and fails if numpy or scipy turned up in `sys.modules`, however
deep the import chain that pulled them in. The check keeps holding as `lib/`
fills up, with no list to remember to extend. The split that filled `lib/` is
done. [code-organisation.md](code-organisation.md) "Splitting the single-file
scripts" holds how `lib/` is laid out and the rules that keep `git blame`
working through a move.

## Units & conventions

- IEQ and audio-optimizer values are stored in 1/16 dB: divide by 16 for dB.
  `geq_maximum_range=192` = 12 dB, the standard graphic-EQ range, confirms it.
- Speaker PEQ gains are already in dB, as float attributes, e.g.
  `gain="-4.000000"`.
- `ieq-amount` is a percentage weight on the IEQ voicing: `scale = amount/100`.
  `10` applies the IEQ curve at 10 % on top of the audio-optimizer correction,
  not at full depth. This `/100` reading is DAX-capture-validated (the
  [`ieq-amount` scaling finding](research/eq-and-frequency-response.md#r-ieq-amount-scaling)).

## Input: Dolby DAX3 XML

The XML is `DEV_0287_SUBSYS_*.xml` or a SoundWire variant, and carries two
processing stages:

- `tuning-cp` (Content Processing) is software DSP: IEQ, graphic EQ, dialog
  enhancer, surround decoder, volume leveler.
- `tuning-vlldp` (Very Low Latency Driver Path) is hardware-level DSP:
  audio-optimizer (speaker correction), speaker PEQ, multi-band compressor,
  regulator.

"XML → parameter mapping" below and cross-device-findings.md cover the XML
fields in detail.

## Output: the plugin chain

Up to eight plugins, chained in this order. HDA devices get seven, because
the bass enhancer is SoundWire-only.

| # | Plugin | Source XML | What it does |
|---|--------|-----------|--------------|
| 1 | Convolver | IEQ target + `audio-optimizer-bands` (gated by `audio-optimizer-enable`) | Min-phase FIR of the combined IEQ + speaker-correction curve, normalised so its loudest band sits at 0 dB |
| 2 | Bass Enhancer (Calf) | IEQ-only SoundWire curve | Harmonic bass restoration on SoundWire speakers. SoundWire-only |
| 3 | Equalizer | `speaker-peq-filters` | 4th-order high-pass at 100 Hz for speaker protection, plus per-channel PEQ bells/shelves/HP-LP |
| 4 | Dialog Enhancer | `dialog-enhancer-amount` | Speech-band EQ boost at 2.5 kHz, from a 2nd equalizer instance. Bypassed by default, because DAX boosted only while speech played on the one device measured; `--enable dialog` opts in ([speech gating](research/adaptive-processing.md#r-dialog-enhancer-speech-gating)) |
| 5 | Autogain | `volume-leveler-*` | Volume leveler. Bypassed by default on HDA, where `--enable autogain` opts in. Active on SoundWire; see below. Placed before the compressor to match Dolby's CP→VLLDP flow |
| 6 | Multiband Compressor | `mb-compressor-tuning` | 1–4 bands of dynamics processing per `group_count` |
| 7 | Regulator | `regulator-tuning` (+ `volmax-boost`) | Per-band limiter, a 2nd MBC instance. `volmax-boost` defaults to its `input-gain` slot: ≈+6 dB, pre-band-limiting. The opt-out `--volmax-slot output-gain` moves the boost post-band-limiting; see below |
| 8 | Limiter | — (+ `volmax-boost` fallback) | Brickwall at -1 dBFS, the safety net, with automatic level regulation holding sustained overs below it ([limiter](research/loudness-and-limiting.md#r-limiter-alr)). Fallback slot for `volmax-boost` when the regulator isn't emitted |

Where a vendor APO config binds the device, up to two more multiband compressors
(`#2`, `#3`), one per dynamics block the layer can build, sit between the
regulator and the limiter. The vendor EQ is folded into the convolver's FIR.
With no regulator, the `volmax-boost` moves from the limiter onto the first of
them. On the PipeWire chain, `--enable virtual-bass` sums its branch after all
of this, so its harmonics skip the vendor layer. Which vendor formats are read,
and what each block becomes: [Vendor tunings](#vendor-tunings).

- **Convolver.** With its loudest band at 0 dB, the stage only ever
  attenuates, and a curve whose peak exceeds `volmax-boost` emits a preset
  quieter than bypass. `--enable level-restore` gives that level back; see
  below. A profile can ship a correction curve and still set
  `audio-optimizer-enable=0`, which drops the curve so only the IEQ voicing
  reaches the FIR. Absent means enabled, as with `speaker-peq-enable`.

`surround-boost` is not mapped to stereo widening. A 2026-06 DAX capture showed
no stereo-width change on 2-channel content. It's a multichannel-virtualization
control, dormant without a surround/object bed. Earlier versions added a Calf
Stereo Tools widener here; see the
[surround→stereo-base factor](research/adaptive-processing.md#r-surround-boost-stereo-base).

Output files:
- `~/.local/share/easyeffects/irs/Dolby-{Balanced,Detailed,Warm}-<8 hex>.irs`
  holds the stereo FIR impulse responses. The suffix is a hash of the impulse's
  own samples, so a regenerated FIR gets a new name. EasyEffects re-reads an
  `.irs` only when the kernel name changes; see "EasyEffects 8.x specifics".
- `~/.local/share/easyeffects/output/Dolby-{Balanced,Detailed,Warm}.json`
  holds the EasyEffects presets.

## XML → parameter mapping

**IEQ curve → FIR.** The 20-value IEQ arrays, e.g. `ieq_balanced`, are the
desired composite frequency response, not individual filter gains. Applied
directly as bell gains, they stack to +20–30 dB at the mids. The script instead
builds a minimum-phase FIR from the combined IEQ + audio-optimizer target, by
cepstral construction with zero added latency. Why FIR over a biquad fit:
[Parametric-EQ approximation of the IEQ curve](research/eq-and-frequency-response.md#r-parametric-eq-approximation),
with the peak/RMS error table. The `.irs` files are RIFF/WAVE: IEEE float32,
stereo, 48 kHz, 4096 samples.

The voicing is the only thing that differs between the Balanced / Detailed /
Warm presets. Their `.json` files are identical apart from `kernel-name`,
because every other stage is derived from profile fields the voicing doesn't
touch. The one exception is `--enable level-restore`, which folds the
per-voicing FIR peak into a gain. The whole 20-band target is weighted by
`ieq-amount/100`, so at the corpus-universal `ieq-amount=10` the three voicings
end up at most ~1 dB apart:

| Pair | Difference |
|---|---|
| Detailed vs Warm | a broad +0.6…0.9 dB tilt across 800 Hz–6 kHz (0.96 dB spread) |
| Detailed vs Balanced | ≤0.5 dB |
| Warm vs Balanced | ≤0.7 dB |

These figures are arithmetic on the Dolby-global curves, matched by FFT of the
generated kernels, 2026-08-25. A subtle difference between the three presets is
expected, not a defect (issue
[#73](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/73)).

**Volume leveler → Autogain.** It maps to EE's EBU R 128 autogain. On HDA it
ships bypassed, and `--enable autogain` opts in. Without Dolby's MI (Media
Intelligence) content steering, it boosts legitimate quiet content and loud
onsets saturate, as measured in the
[2026-07 default-flip attempt](research/adaptive-processing.md#r-autogain-default-flip).
On SoundWire it ships active with gentler settings. Settings are always
preserved so users can toggle it in the GUI.
- `volume-leveler-out-target` -320 (1/16 dB = -20 dBFS) → -20 LUFS target. The
  SoundWire path subtracts a further 6 dB of safety headroom. That offset is
  invented:
  [conservative-autogain offsets](research/adaptive-processing.md#r-conservative-autogain-offsets).
- `volume-leveler-amount` (0–10) → `maximum-history` window. HDA:
  `max(30 − 5·amount, 10)` s. SoundWire: `max(40 − 4·amount, 15)` s. Both
  formulas are invented:
  [leveler→autogain window](research/adaptive-processing.md#r-leveler-autogain-window).
- `silence-threshold` = -50 dB on both paths. It is invented but field-confirmed
  in issue
  [#25](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/25),
  and capture-measured. It stops the leveler winding up its gain over
  near-silence. At EE's -70 dB plugin default, that wind-up crackled short
  notification sounds.
- autogain `reference` = Geometric Mean (MSI). It combines momentary,
  short-term, and integrated loudness for balanced behaviour.

**MB compressor → Multiband Compressor.** Each band is a 6-value tuple:

| Index | Field | Units | → |
|-------|-------|-------|---|
| 0 | Crossover band index | index into the 20-freq table | e.g. 3 → 328 Hz |
| 1 | Threshold | 1/16 dB | -103 → -6.4 dB |
| 2 | Gain coefficient | Q15 | `ratio = 1/(coeff/32768)`; 32767 ≈ bypass |
| 3 | Attack | Q15 block-rate | `tau = -1/(blocks·ln(coeff/32768))` |
| 4 | Release | Q15 block-rate | same decode |
| 5 | Makeup gain | 1/16 dB | 32 → +2 dB |

Only the first `group_count` of the four `band_group_N` slots are decoded,
capped at LSP's 8-band ceiling. Block rate assumes 256 samples @ 48 kHz.

A threshold below −60 dB, the deepest LSP and EasyEffects accept, runs at
−60 dB. That band's makeup drops by `(−60 − threshold)·(1 − 1/ratio)`, which
keeps the tuning's gain on signals above −60 dB. Below the tuning's threshold
the band plays quieter than the tuning by that amount, and makeup itself stops
at −60 dB. The regulator and the Surface
APO dynamics apply the same floor
([threshold floor](research/adaptive-processing.md#r-threshold-below-lsp-floor)).

**`volmax-boost` → loudness makeup.** `volmax-boost`, e.g. 96 = +6 dB, is the
ceiling of Dolby's MI-steered VolMax. With no MI leveler to apply it
dynamically, the script applies it statically as the regulator's `input-gain`.
When the regulator isn't emitted, it falls back to the brickwall limiter's
`input-gain`. `--disable volmax` disables it.

Neither placement is Dolby-derived. `volmax-boost` is itself a CP-stage leveler
ceiling, so applying it at the VLLDP-stage regulator is a pragmatic
approximation. The default `input-gain`, from issue
[#23](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/23),
feeds the boost into the regulator's per-band downward compression. That tames
the boosted low end before the brickwall, eliminating a measured low-end
distortion. `--volmax-slot output-gain` is the opt-out. It moves the boost after
the regulator, the pre-#23 placement, so the full loudness makeup goes straight
into the brickwall. Use it for A/B, or to recover loudness if a device's
regulator over-tames the bass. The default flipped to `input-gain` after a
second, aggressive-regulator device confirmed it stays clean and loud: the
ThinkPad X13 Gen 6 of issue
[#23](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/23).
See
[`volmax-boost` slot](research/loudness-and-limiting.md#r-volmax-boost-slot).

The opt-out has its own field confirmation: issue
[#44](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/44)'s
Yoga Slim 7 14ARE05 runs an eleven-band regulator whose deepest threshold is
−30.9 dBFS. There `output-gain` measured +6.8 dB more bass below 300 Hz than the
default, and less out-of-band energy, since the bands no longer see the boost.
The reporter found the result on par with Windows. Their Windows capture of the
same loud-bass stimulus (2026-08-24) then put Dolby itself 0.2–2.8 dB below
bypass on sustained bass. That is within 0.6–3.3 dB of `output-gain`, and 7–9 dB
above the default. On this tuning the opt-out is therefore the DAX-faithful
order, not merely the louder one. Two field devices thus prefer opposite slots.
The default stays `input-gain`, and no XML-derived rule picks the slot yet
([Why bypass has more bass than the preset](research/loudness-and-limiting.md#r-deep-threshold-bass-loss)).

**Regulator → per-band limiter.** A second MBC instance is configured as a
limiter, with Peak sidechain and a 20 ms attack, set from DAX captures on two
devices
([attack experiment](research/loudness-and-limiting.md#r-fixed-dynamics-constants)).
Its thresholds come from `regulator-tuning` `threshold_high`, in 1/16 dB per
band. The 20 Dolby bands are grouped into ≤8 zones of identical threshold.
Tighter low-frequency limiting protects laptop speakers from sub-bass they can't
reproduce.
- `regulator-distortion-slope` → limiting ratio `1/(1-slope)`.
- `regulator-timbre-preservation` → knee `-6 × timbre dB`.
- `threshold_low` and `stress-amount` are not used.

`threshold_high` is read from a direct `value=`/`preset=` on most devices. On
the newer SoundWire per-channel schema, it is read from its `<ch_00>`
sub-element, the `ch_00`/`ch_01` form the audio optimizer also uses. An empty
tuning falls back to no limiting, with a warning.

## Profile differences

| Profile | IEQ | IEQ curve | Volume leveler | vlldp AO/PEQ | MB compressor |
|---|---|---|---|---|---|
| dynamic | yes | ieq_balanced | on (amount 2) | shared | enabled |
| movie | no | — | off | shared | enabled |
| music | yes | ieq_balanced | on (amount 2) | shared | enabled |
| game | no | — | on (amount 2) | shared | enabled |
| voice | no | — | off | **different** | disabled |

All non-voice profiles share the same audio-optimizer and speaker PEQ. Voice has
different AO tuning and simplified PEQ. The MB-compressor threshold varies
slightly per profile. Wider corpus distribution: cross-device-findings.md.

Without `--profile`, the script builds the endpoint's first profile. A few XMLs
name the one the device ships on under Windows, in
`<setting><default_profile>`. That field is read but not acted on: a run reports
the mismatch and suggests `--profile <name>` (issue #46).

`<setting><geq_maximum_range>` is likewise read for diagnostics only. It is the
widest per-band gain the file expresses, and 192 = 12 dB is assumed when it is
absent. A run warns when the tuning's largest boost both reaches that range and
lands on a band the regulator leaves at a 0 dB threshold. The boost and
`volmax-boost` then reach the brickwall with no per-band limiting. It stays
quiet when the default coupled-bands mapping limits any zone. Under
`--enable level-restore` it fires whatever the boost's size.

## EasyEffects 8.x specifics

- Presets live in `~/.local/share/easyeffects/output/`, not `~/.config/`. The
  Flatpak keeps them in
  `~/.var/app/com.github.wwmm.easyeffects/data/easyeffects/output/`.
- IR files live in `~/.local/share/easyeffects/irs/` with the `.irs` extension,
  not `.wav`. The Flatpak keeps them in `.../data/easyeffects/irs/`.
- The `not ~/.config/` above holds because EasyEffects 8.0.0 moved presets,
  IRs, rnnoise models and autoload profiles to `XDG_DATA_HOME` (upstream
  `d8a50b529`). It migrates 7.x copies there on *every* start, trashing the old
  folder. The settings db stayed at `~/.config/easyeffects/db/`. That is why
  this tool's rc and preset paths are rooted differently, and why
  `config/easyeffects/` outlives the migration and can't say which layout wrote
  it.
- Those two spellings are the XDG *defaults*. EasyEffects asks Qt
  (`QStandardPaths`) for both roots and never reads the variables itself. So
  `XDG_DATA_HOME` and `XDG_CONFIG_HOME` move its tree, and this tool follows
  them through `lib/xdg.py`. Only an **absolute** value counts. The basedir
  spec calls a relative one invalid and Qt ignores it, so treating "set" as "use
  it" would split the two apart. The leaf is `easyeffects` under both roots with
  no organization component, because upstream never sets `organizationName`.
  The db path is generic `ConfigLocation` plus a literal `/easyeffects/db`
  (`src/db_manager.cpp`), not `AppConfigLocation`. The two are the same
  directory today, but not if that ever changes.
- The Flatpak roots are exempt, and stay anchored to `$HOME`. Inside the
  sandbox, `flatpak run` overrides all four XDG variables to point at
  `~/.var/app/<app id>/`. It passes the host's values through as `HOST_XDG_*`
  (`man flatpak-run`). What the user set outside therefore says nothing about
  where a sandboxed EasyEffects reads. The one Flatpak path that *is* an XDG
  path is the per-user install root, `$XDG_DATA_HOME/flatpak`. `--doctor` walks
  it to find a deployed app's version.
- The convolver uses `"kernel-name"`, the filename stem, not the deprecated
  `"kernel-path"`.
- The convolver re-reads its `.irs` only when `kernel-name` *changes*. A
  same-name rewrite keeps the old impulse in memory through a preset reload or
  a GUI re-pick. The generator therefore names each impulse after a hash of its
  samples. It removes the impulses earlier runs of the same preset left behind,
  unless something still names one: another preset, a `--no-copy-irs` PipeWire
  conf, or EasyEffects' own saved settings. EasyEffects restores the
  convolver's kernel name from its config db on start. A still-named impulse
  is kept and reported.
- A run that finds EasyEffects listening on
  `$XDG_RUNTIME_DIR/EasyEffectsServer` loads the preset into it over that
  socket. Native installs have that socket since 8.0.9. The run loads the preset
  EasyEffects is already playing, if that is one of this run's. Otherwise it
  loads the starting preset, unless EasyEffects is on the `Nothing` bypass
  preset or the default output isn't an internal speaker. In those two cases it
  leaves them as they are and says so. It reads back the loaded preset and the
  convolver's kernel name as the receipt, and says what it did or what to do.
  Flatpak installs, whose socket is inside the sandbox, and older installs get
  the manual step instead. `--no-reload` opts out. The run then says what
  EasyEffects keeps playing and which preset to pick.
- EasyEffects watches its impulse and preset directories and rebuilds the list
  models on every change. It emits row inserts inside a model reset, which Qt
  forbids. With the window open on the Convolver page, a burst of changes
  crashes it: a segfault in libQt6Qml, the frames of upstream
  wwmm/easyeffects#5120. It was reproduced on 8.2.8 / Qt 6.10.2 and reported
  on 8.2.9 / Qt 6.11.2
  ([#95](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/95)).
  Upstream fixed it in wwmm/easyeffects#5306, in no release as of
  2026-09-13. Unless the installed version is past 8.2.9, a run therefore sends
  `hide_window` over the socket before writing, whenever a socket is there to
  take it, and prints a line saying so. Nothing can narrow that. The page
  EasyEffects last showed reaches `db/easyeffectsrc` only on window hide,
  close, quit, or a 30 s timer that runs while the window is open. So it is
  stale exactly when a page was just opened. The socket cannot be asked, and
  hiding an already-hidden window is a no-op. The hide request is
  one-way: nothing answers it. A run never sends `show_window`, since nothing
  says whether the window was open.
- `--doctor` applies the same rule to its selected-preset check. The `Nothing`
  bypass preset is a WARN on the speakers and on an output it cannot classify.
  On a *confidently* non-speaker output, it is the state `--autoload` installs
  on purpose. The check then reports what the speakers autoload instead. It is
  PASS, naming that preset, when an autoload entry maps a speaker sink to one
  this script generated. It is UNKNOWN when nothing settles it. The gate is
  `sinks.sink_kind(...) == "other"`, never `not is_internal_speaker(...)`. That
  one folds "don't know" into "not a speaker", and would drop the warning on a
  failed probe. On the same confident gate, a generated preset loaded on a
  non-speaker output is a WARN: a speaker tuning playing on a headset or HDMI.
  Its remedy follows the fallback setting, since `--autoload` turns the
  fallback on only when it is off.
- The equalizer is parametric only, with no graphic-EQ mode. It is the LSP
  plugin.

EE 7 uses an incompatible preset format. On EE 7 the speaker-correction filter
loads nothing. Use the Flatpak if your distro still ships EE 7.

## Uninstall (`--uninstall`)

Each route removes only files that an existing ownership test proves are its
own. The EasyEffects route's tests live in `lib/preset/uninstall.py`, and the
PipeWire route's in `lib/pipewire/uninstall.py`.

- **Preset:** the `_generator` stamp, or a convolver naming our hashed
  `<preset>-<8 hex>` impulse. That is the doctor's `is_generated_preset`
  without its bare-name match, which a user's own `MyRoom` preset on
  `MyRoom.irs` would pass. A match on the impulse name alone is listed as
  re-saved.
- **`Nothing.json`:** only with the stamp, and only when no remaining autoload
  entry names it.
- **Impulse:** a name `kernel_belongs_to` ties to a removed preset. The legacy
  unhashed `<preset>.irs` counts only beside a stamped preset. It is kept while
  a remaining preset or PipeWire conf names it. It is also kept while
  EasyEffects' `convolverrc` names it, unless this run emptied a running
  EasyEffects' chain first.
- **Autoload entry:** it names a removed preset, in the autoload folder of the
  tree being scanned. With `--output-dir` elsewhere, a match in EasyEffects'
  own folder is listed as left in place.
- **Fallback Preset:** it is on and names our `Nothing`, that `Nothing` is
  being removed, and the tree has a settings file. The run flips only
  `outputAutoloadingUsesFallback`. A running EasyEffects keeps that edit: it
  saves only the keys it changed itself, and it reads the file when it starts.
- **Conf:** it starts with `CONF_HEADER_MARK`. Its impulse is removed only as
  the `<conf dir>/<node>.irs` or `<conf dir>/<conf stem>.irs` copy, and only
  when no other conf names it.

The steps run in this order: switch a running EasyEffects to an empty preset,
then the rc edit, autoload entries, presets and impulses. A failed rc edit stops
the run before anything is removed. Each file is re-tested just before it goes.
Files go to the Trash through `gio trash` when it is installed. A failed trash
is reported, not turned into a delete.

EasyEffects keeps the active chain in its own settings, not in the preset file.
Its own `Manager::remove` only resets `lastLoadedOutputPreset`. So the empty
preset is loaded over the socket, which only a native EasyEffects answers.
Otherwise the run prints a manual step.

## Vendor tunings

Two vendor formats are read. Microsoft's Surface APO adds to a Dolby tuning. A
Sonitude preset stands alone, on a laptop with no Dolby file.

### Surface APO

It is on by default, and `--disable vendor-apo` leaves it out:

| Surface APO block | Becomes |
|---|---|
| `MainEQ` biquads, every `MainEQ*` block in file order | Folded into the FIR, its target floored 40 dB under its peak |
| `VolumeDepMBDRC4`, `VolumeDepMBDRC` | `multiband_compressor#2`, at volume state 0, read (unvalidated) as full volume; bands above 20 kHz dropped |
| `Crystal`, `Crystal1`, `Crystal2` | `multiband_compressor#3`, one limiter band per resonance; entries identical in the fields it uses collapse. With more than 6 resonances, or two sharing an F0, the whole stage is left out and the run says so |
| `VolumeDepLS/PN/HS`, hold times, `OutputLimiter`, any other block | Not reproduced; the run lists them |

### Sonitude input

A laptop that ships no Dolby file can voice its speakers in a Sonitude APO
preset instead. The run reads that preset as the device's whole tuning. It
builds one preset per content mode, each the convolver then the limiter of the
chain above. Flags that act on a Dolby stage are refused.

The run finds the tuning in one of two places:

- **A driver download or one of its archives**, passed in place of the XML.
  The archives are `SEAPODAT.<bus>.FUNC_01-VEN_<v>-DEV_<d>.zip`. A download
  that also holds a Dolby XML takes the Dolby route.
- **An installed Windows**, through auto-detection or `--windows`. A Dolby
  file there that matches the device wins. Otherwise the run reads the
  `snapo64ext.inf_amd64_*` package folder in its DriverStore. Of several
  package versions, the newest by its INF's `DriverVer` is read.

| Sonitude field | Becomes |
|---|---|
| `SSIDMAP.bin` | Picks the preset by codec subsystem ID |
| Endpoint 0 `EFX/AnyOutput/<mode>/Preset.bin` curves, L and R | Folded into the FIR as cuts only, on a 1/24-octave grid from 10 Hz, its target floored 40 dB under its peak |
| The same file's high-pass, stage 5 keys 19/20 | When on, a 4th-order Butterworth at its corner replaces the curve at and below the corner. When off, the curve's own low end is kept |
| Dynamics, psychoacoustic bass, the 10-band equaliser, the headphone and posture modes | Not read |

Where the curve's first rise of more than 6 dB between neighbouring points
starts within one grid point above the corner, that point is replaced too.

Where both an `INTELAUDIO` and an `HDAUDIO` archive bind the device to
different curves, a machine running SOF takes `INTELAUDIO` and any other takes
`HDAUDIO`. The run says which it used and names the other archive. One archive
passed alone is the one read.

Each content mode is a profile:

| `--profile` | Content mode | Preset |
|---|---|---|
| `music`, the default | `AnyContent` | `Sonitude-Music` |
| `movie` | `Movie` | `Sonitude-Movie`, marked experimental |
| `voice` | `Voice` | `Sonitude-Voice`, marked experimental |

`--all-profiles` builds every mode the archive holds, and `--list` names them. A
mode the archive lacks is left out, except `music`, which the run requires. A
mode whose built curves are flat within 0.05 dB, with its high-pass off, changes
nothing, so no run builds it: the default becomes the first mode that changes
the sound, and `--list` marks it. Each preset's FIR is normalised so its loudest
point sits at 0 dB. The level difference between modes is therefore not
reproduced.

The run reports each stage on one line, as `built`, `approximated` (built,
knowingly not as the file states it) or `not reproduced`. A Sonitude preset
reports:

| Stage | Status | Says |
|---|---|---|
| EQ curve | built | its boosts left out, where it has any (the evidence covers Music; untested for Movie and Voice) |
| high-pass | built | its corner, or that it is off |
| compressor and limiter | not reproduced | not read yet |
| psychoacoustic bass | not reproduced | not read yet; on one laptop the tuning adds harmonics to the deepest bass, likely from this stage |
| 10-band equaliser | not reproduced | not read; taken to be the app's user equaliser, flat in the one preset checked |
| outside this tuning | not reproduced | on one laptop Windows also shapes the sound with its audio enhancements off (measured at 50 % volume); its source is unknown |

Output files are `output/Sonitude-<Profile>.json` and
`irs/Sonitude-<Profile>-<8 hex>.irs` under `~/.local/share/easyeffects/`.
Every mapping here is unvalidated: see
[Validated vs unvalidated mappings](#validated-vs-unvalidated-mappings).

## Not implemented (and why)

- **`filter_coefficients`**: a base64 biquad blob in `tuning-vlldp`.
  Investigated, it is VLLDP-internal analysis filters, not audio-path EQ. The
  audio-optimizer + PEQ already capture the same correction
  ([`filter_coefficients` as an audio EQ source](research/eq-and-frequency-response.md#r-filter-coefficients-blob)).
- **`regulator-stress-amount` / `threshold_low`**: secondary regulator
  parameters. Only `threshold_high` drives the per-band limiter.
  `isolated_band` *is* implemented, and on by default; see the unvalidated list
  above.
- **The level the FIR is normalised by**: the convolver's peak normalisation is
  not compensated on the default path. `volmax-boost` is the only static gain
  that puts level back. On tunings whose peak exceeds it, the preset plays below
  bypass. The experimental `--enable level-restore` flag hands the normalisation
  scalar back to the regulator's gain slot. That scalar is XML-derived: it is
  `make_fir`'s own `peak_db`. The flag was **heard on one device only**,
  2026-08-18, where loud speech picked up audible artifacts
  ([Giving back what normalisation removed](research/loudness-and-limiting.md#r-level-restore),
  issue
  [#50](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/50)).
  Default output is unchanged.
- **Virtual Bass Enhancement on HDA**: DAX synthesizes odd-dominated bass
  harmonics on internal speakers (issue
  [#14](https://github.com/antoinecellerier/speaker-tuning-to-easyeffects/issues/14)).
  The default output still doesn't. The experimental `--enable virtual-bass`
  flag builds the measured chain on the PipeWire path only. EasyEffects' serial
  pipeline cannot express the parallel branch, as verified against the EE source
  2026-08-21. In the chain, two LSP brick-wall band-passed arms over the
  `virtual-bass-src-freqs`→`mix-freqs` split go into a Calf Saturator. They are
  premixed at the `virtual-bass-subgains` weights, where the −192 slot = that
  sub-band off. The mix is band-limited to `virtual-bass-mix-freqs` and summed
  at the XML's `virtual-bass-overall-gain`. The gains are sixteenth-dB. The
  fields are corpus-frozen, identical in every XML measured. That is what keeps
  this opt-in under the XML-only invariant. Two saturator constants (`drive=4`,
  `blend=−10`) are measurement-calibrated against the DAX capture, not
  XML-derived. The chain is all-IIR with no look-ahead, so it adds zero latency.
  The [DAX virtual-bass finding](research/virtual-bass.md#r-dax-virtual-bass)
  holds the measured score, guards, and the on-device listening result. The
  offline reproduction is `tools/measure_ee/render_vbe_chain.py`.
- **Always-inert / out-of-scope XML fields**: deliberately ignored. They're
  always zero/disabled on the modelled endpoints, are DSP internals with no
  EasyEffects equivalent, or concern multichannel/subwoofer routing irrelevant
  to stereo laptop output:
  - `pregain`/`postgain`/`calibration-boost`/`system-gain`, all 0 dB
  - `bass-extraction-*`
  - `virtual-bass-*` on the default path. `--enable virtual-bass` opts in; see
    the VBE entry above.
  - `volume-modeler-*`
  - `graphic-equalizer-*`
  - `surround-*` / virtualizer-geometry
  - `mi-*-steering-enable`
  - `output-mode`/`mix_matrix`/`processing_mode`
  - `init-info` sizing
  - CP-level `audio-optimizer-bands` / `regulator-tuning`, always zero. vlldp
    has the real data.
  - `mb-compressor-agc-enable` / `mb-compressor-slow-gain-enable`
  - `woofer-regulator-*`
  - `band_20_freq` @ 44.1 kHz. The script is 48 kHz only.
  - `ieq-bands-set`. The script generates all three IEQ variants.
- **Other driver-download shapes**: a `.cab`, an archive inside another
  except in an ASUS-style `.exe`'s resources, which is followed one level
  deep, and an already-unpacked folder passed in place of the XML. No download
  in the corpus needs the first two, and `--windows DIR` covers the third. A
  `.msi` is unpacked in full before only its tuning files are kept, since
  `msiextract` has no member filter. For the Surface Pro 9 package that takes
  about 3.5 GB of free space while it unpacks.

## The 48 kHz assumption

The pipeline is built at 48 kHz throughout (`lib/preset/bands.py`
`SAMPLE_RATE`). The FIR is designed at it, the `.irs` is written at it, and the
MBC time constants divide by it. That is a property of what we emit, not a
limitation of the XML. The runtime consequence sits one layer down, in
EasyEffects. It resamples the convolver kernel to whatever rate the PipeWire
graph runs at and compensates no gain. On a graph above 48 kHz the preset
therefore plays hot by the ratio of the two rates. A run and `--doctor` both
warn. The PipeWire filter-chain path is unaffected. Measurement and mechanism:
[A preset that plays hot](research/easyeffects-and-pipewire.md#r-convolver-resample-gain).
